## 一、先做：去哪吃問題單

依據 `問題單-去哪吃菜系篩選-待排程.md`。這是**唯一一件違反產品規則**的既有缺陷。

根因在 `FoodRotate/Services/NearbySearch.swift:190-199`：

```swift
let query = keyword.isEmpty ? "餐廳" : keyword
var places = try await searchPlaces(dish: query, near: location)
if places.isEmpty, !keyword.isEmpty {
    places = (try? await searchPlaces(dish: "餐廳", near: location)) ?? []
}
```

**這個退回是靜默的** —— 使用者選了「歐陸」，拿到的是一般餐廳，畫面上沒有任何說明。
違反「放寬要老實說明」那條規則。

| 做什麼 | 不要做什麼 |
|---|---|
| 菜系在「去哪吃」降級為**搜尋關鍵字**，UI 用語一起改（不要再叫「篩選」） | **不要**用關鍵字去過濾 MapKit 回傳的結果 —— 店名裡沒有菜系資訊，濾不出真相，只會製造另一種假象 |
| 退回一般餐廳時**顯示提示框**，明講「找不到 X 的店，改列附近的餐廳」 | 不要接 Google Places（金鑰與計費，不在這階段） |
| 幾個 MapKit 查不到的菜系做搜尋詞翻譯表（例：歐陸 → 西餐／牛排／義式） | 不要動「吃什麼」模式的任何一行 |

**驗收**：十個菜系逐一實機測過並記錄結果；「吃什麼」模式行為零變化。

## 二、S3-1：結果頁架構改動（不等規格）

`matchedGeometryEffect` 跨不過 `.sheet` 邊界（S2 查證過的技術事實），所以
`RotateView.swift:337` 那個 `.sheet` 要換成同一個 ZStack 裡的 overlay。

### 換掉之後系統不再免費提供的四件

| 項目 | 說明 |
|---|---|
| 下拉關閉手勢 | 自己做。**視覺與觸發距離由設計定**，先把手勢骨架搭好 |
| 圓角與頂端把手 | 自己畫，數值等規格 |
| 內部 `NavigationStack` 與「完成」按鈕 | `ResultSheet` 現在靠 sheet 的導覽結構，要重新安排 |
| 再開出去的「附近的店」 | `ResultSheet.swift:79` 那個 `.sheet`，overlay 之後要確認還開得起來、關得掉 |

**這是 S3 最容易低估的一項。** 動效參數只是表面，真正的工作是換掉呈現方式。
你可以先把架構換好、視覺維持現況，等規格到了再套 —— 這樣兩段風險不會疊在一起。

## 四、S4：⚠️ 這一階段離產品規則最近

`FilterBar` 就是那八條規則的門面。**`FoodPicker`／`FilterBar`／`FoodEditorView`
在 S1、S2 都是零變更，S4 會第一次真的動它們。**

### 三條紅線

| 規則 | 具體要求 | 現在在哪 |
|---|---|---|
| 「去哪吃」只顯示菜系那一列 | `activeDimensions` 這個參數**要繼續有作用**，不能因為改版面就把六個維度全列出來 | `RotateView.swift:301` |
| 收合狀態要看得到條件摘要 | 不能省成一個「篩選」按鈕，否則使用者會以為 App 隨便給 | `FilterBar.swift` |
| 忌口永遠不會被自動放寬 | `FoodPicker.pick()` 第一步**一個字都不要動** | `FoodPicker.swift` |

`FoodPickerTests` 那五支測試就是為這一刻寫的。**改完它們必須還是綠的，
而且不准為了讓它們過而改測試。**

### 四項工作

1. `FilterBar` 改網格（34 個標籤展開後一屏看完、忌口區視覺權重不同）
2. `FoodCardList` 改高密度列（五個操作：改名、刪除、永久排除、開地圖、打電話要放得下）
3. `FoodEditorView` **沿用同一套標籤元件**，不要另做一套
4. 候選清單卡片的 emoji 換成 S2 的圖示系統 + 菜系角標
