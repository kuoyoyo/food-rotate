## 三、P1-3 的分界線：這是這一批最好的一段

```swift
static func isNotFound(_ error: any Error) -> Bool   // placemarkNotFound / directionsNotFound
```

註解寫的：

> 分不出來就只能二選一：把服務故障說成「沒有店」（假裝知道），
> 或把「沒有店」說成故障（嚇人又不給 fallback）。**兩個都不對。**

**你把整段容錯的正確性收斂到一個函式上**，而那個函式的存在理由是產品原則不是技術方便。逐詞處理也對：not-found → 該詞貢獻 0 繼續；服務端錯誤 → 記下第一個、**不靜靜變成「沒有店」**、其餘的詞照樣查。

「東南亞查泰式＋越南料理，泰式找到 3 家、越南料理拋 not-found，以前那 3 家跟著消失」—— 這個具體場景寫在註解裡，比任何抽象描述都有用。

## 四、⚠️ `LoadingActivityController.cancel()`：**核可，而且我不接受你給的退路**

你說「要退回的話說一聲，我改成沿用 `end(stage: .failed)`」。**那個退路本身是錯的，我明說。**

> 把使用者的取消說成失敗，跟把「附近沒有店」說成「服務故障」是同一種錯。

**這句話就是核可的理由。** 鎖定畫面上留一張寫著「失敗」的卡四秒，但沒有任何事情失敗 —— 那是對使用者說謊，跟這個專案從「去哪吃」問題單以來守的原則直接衝突。

而且這不是「順手多做」：**修 P1-1 必須收掉切模式時的 Live Activity**，而原本的 API 只給得出 `.failed`。沒有 `cancel()` 就沒辦法正確地修 P1-1 —— 它是必要條件，不是額外功能。

**判斷「超出派工單」與「派工單漏講」的界線**：如果不做它，被指派的那一項就做不對 —— 那就是漏講。你標出來問是對的，但這一項不用退。
