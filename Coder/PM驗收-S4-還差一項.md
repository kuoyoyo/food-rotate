## 一、🔴 阻擋項：`.swipeActions` 掛在不是 `List` 的地方

### 現象

我實機左滑兩次（一次快、一次慢速六段），**完全沒有反應**。

### 原因（我從程式碼確認）

`FoodCardList.swift:120` 的 `.swipeActions(edge: .trailing)` 掛在 `FoodRow` 上，
而 `FoodRow` 是放在 `FoodCardList.swift:39` 的 **`VStack(spacing: 0)`** 裡：

```swift
VStack(spacing: 0) {
    ForEach(Array(items.enumerated()), id: \.offset) { index, item in
        if index > 0 { Divider()... }
        FoodRow(...)          // ← .swipeActions 在 FoodRow 內部
    }
}
```

**`.swipeActions` 只在 `List` 的 row 上有作用。** 掛在 `VStack` 的子 view 上是一個
無效修飾符 —— 編譯得過、不會當、不會有任何警告，**但什麼都不會發生**。

### 這一項為什麼要退回

它跟上一輪的 hero 拖曳是**同一類**：列在「已實作，未實測」，但實際上不是「還沒驗」，
是**根本不會動**。差別在於 hero 那次是掛錯層級（會動、只是範圍窄），這次是完全沒作用。

你這次的分類方法是對的，我認可 —— 但「已實作」這個前提本身要成立。
`.swipeActions` 在 `List` 以外沒有效果，這是可以在寫的當下就知道的事，不需要觸控才發現。

### 兩條路，你選

| | 做法 | 代價 |
|---|---|---|
| **A** | 自己做左滑：`DragGesture` + 位移 + 露出 `negative` 底的按鈕 | 要自己處理手勢與捲動的衝突（跟 S3 的 hero 拖曳同一類問題，你已經有經驗） |
| B | 拿掉左滑，只留 `⋯` Menu | 少一個快捷。設計說「這輪不要是最常用的一個，每次都要開 Menu 太慢」 |

**我傾向 A**，但如果你評估成本高，B 也可以 —— 那要回頭跟設計說一聲，
因為左滑是他規格裡明寫的。**不要留著一段不會生效的程式碼。**

## 四、兩件你提的，我的回覆

### 1. 「一屏看完」只在預設字級成立 —— 同意

放大就自然捲動，無障礙優先於版面。這是設計規格裡就寫明的可接受降級，不用另外做限制。

### 2. 「一定不會出現」那句小字留著 —— **同意，你判斷對了**

> 外觀說的是「這一區不一樣」，那句話說的是「哪裡不一樣」。

而且你補的第二個理由更重要：**那是產品規則第一條在畫面上的唯一說明。**
染色只能表達「注意」，表達不了「這一項不會被自動放寬」。拿掉會少掉一個保證。
