## 二、「圖示正立」是這一輪的關鍵

正立之前與之後是兩個東西。修正前我在 12 格下看到的是一團認不出的線；正立之後：

| 圖示 | 實機辨識 |
|---|---|
| 飯食 | 碗 + 飯山 + 三顆飯粒，**一眼是飯** |
| 麵食 | 碗 + 斜插筷子，跟飯食明確分得開 |
| 湯的 | 湯匙，輪廓乾淨 |
| 鍋物 | 寬鍋 + 兩側把手 + 蒸氣 |
| 小吃 | 竹籤三串 |
| 麵包餅皮 | 楔形切角 + 點狀質地 |
| 肉食 | 帶骨的肉 —— **最弱的一個**（設計自己也標了） |

設計那句判斷成立，值得留著：

> emoji 耐轉是因為它是彩色色塊，靠質地與顏色辨識；線稿靠的是輪廓方向。
> 一個碗倒過來就不是碗。

**先前「辨識度不足」的歸因是錯的** —— 主因是旋轉，不是尺寸。當時沒有下結論、
要求先正立再判斷，是對的順序。

## 三、一個誤報要更正（PM 自己的）

驗收過程中我一度以為「App 不跟隨系統深色模式」是 S2 的回歸。
**拿 S1 的 build 在同一台模擬器上對照，也是淺色** —— 所以是模擬器狀態問題，不是回歸。

工程先前報告寫「`simctl ui appearance dark` 這次對 App 沒生效」，**他是對的**。
重開模擬器之後深色正常。

> 記一筆方法：模擬器改 appearance 後，**要 shutdown/boot 才會套用到 App**，

## 四、通過但要記著的兩件（不擋 S3）

### 1. 同一盤上飯食圖示會大量重複

12 格實測有一輪出現 **8 個相同的飯碗圖示**。

這是**設計刻意的結果**，不是缺陷 —— 圖示只表達類型、身分交給兩行全名（S1a 已核可）。
資料庫本身飯食類佔比就高。

但視覺上值得設計自己看一眼：原本的問題是「8 格 77% 機率撞 emoji」，
現在變成「按設計必然撞圖」。差別在於**名字現在是完整的**，所以身分不會混淆。
**PM 認為可接受，但這是設計該親眼確認的取捨**。

### 2. 「肉食」是九個圖示裡最弱的

設計在規格裡自己標了。目前是帶骨肉的輪廓，在 12 格下接近下限但仍可辨。

1. **主色測試的寫法** —— 發現第一版會誤報後不調鬆讓它過，改寫探針找到
