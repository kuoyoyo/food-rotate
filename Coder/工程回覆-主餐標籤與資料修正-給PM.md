## 二、第 3 點的差異：是 0 個問題，不是 1 個

提案預期「剩 1 個提醒（低卡餐盒缺菜系，刻意保留）」。實作後是 **0 個**，因為豁免機制
直接把那則提醒**消掉**而不是保留它。

這是刻意的，理由就是提案第三節第 3 點自己寫的那句：「否則這個提醒會永遠叫，久了就沒人看。」
一個永遠有 1 則的檢查，跟一個永遠是 0 的檢查，前者沒辦法讓人一眼判斷「有沒有新問題」。
把刻意的例外歸零，新的缺漏才會跳出來。

「刻意保留」這件事沒有消失，它移到了程式碼裡有名有姓的地方（見下節）。

## 三、豁免機制怎麼做的

`FoodDataAudit.cuisineExemptions`：**`id` → 為什麼**，value 是原因字串不是 `Bool`。

```swift
static let cuisineExemptions: [String: String] = [
    "low-calorie-bento": "便利商店的低卡餐盒不屬於任何一國菜，改由圖示系統的 fallback 接住"
    // 出處：`PM/PM提案-7道菜補標籤-待核可.md` 第一節，2026-08-11
]
```

三個設計取捨，都是為了讓這份清單不要爛掉：

1. **強迫寫理由。** 用字典而不是 `Set`，加進來的人必須交代為什麼，這份清單才不會變成
   「檢查太吵就丟進去」的垃圾桶。
2. **豁免只擋菜系，不擋吃法。** 豁免的理由是「不屬於任何一國菜」，不是「什麼標籤都不用掛」。
   低卡餐盒的「輕食」還是要在，圖示才推得出來。
3. **豁免會自己喊過期。** 哪天有人給低卡餐盒補了菜系，檢查會反過來說「把它從
   `cuisineExemptions` 移除」。沒有這道，一個沒意義的豁免會留著，
   下次真的有人把菜系拔掉就沒有人知道。

### 為什麼放在程式而不是 `foods.json` 加一個欄位

加欄位會動到 `FoodItem` 的 `Codable`，那是**出貨到 App 裡、而且要對翻 Android** 的型別；
為了一個 DEBUG 期的開發工具去改它不划算。豁免是「檢查的設定」不是「這道菜的屬性」，
放在檢查旁邊比較誠實。
