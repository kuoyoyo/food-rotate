# 問題單 — 「去哪吃」的菜系篩選不準，且靜默退回違反產品規則

**回報**：kuoyo，2026-08-11（實機操作發現）
**分類**：既有缺陷（基準點 `6b2a37f` 就存在，非 S1 造成）
**排程**：**S2 驗收通過後、S3 之前**（kuoyo 裁示）
**方向**：**誠實降級為搜尋詞**（kuoyo 裁示）

---

## 一、重現

1. 切到「去哪吃」
2. 菜系選「歐陸」
3. 轉盤上出現「麻辣鴛鴦火鍋」

---

## 二、根本原因：MapKit 沒有菜系欄位

`RotateViewModel.findRestaurants()` 把選到的菜系標籤串成字串，直接餵給 MapKit：

```
filter.tags(in: .cuisine) → "歐陸" → MKLocalSearch.naturalLanguageQuery
```

`NearbySearch.swift:190` 的註解寫著「它對『日式』『韓式』這類詞的理解比想像中好」。
**那個判斷對日式、韓式成立，對「歐陸」不成立** —— 「日式」大量出現在台灣的店名裡
（日式拉麵、日式燒肉），MapKit 比對得到；「歐陸」幾乎不出現在店名裡，MapKit 退化成
模糊比對，回一批沾邊的餐廳。

**我們從來不是在篩菜系，只是拿店名做文字比對。** 這跟營業時間是同一類問題
（`大改紀錄` 3.8）：MapKit 給不出來的東西，就不該表現得像我們知道。

---

## 三、更嚴重的一點：靜默退回違反了八條規則之一

`NearbySearch.swift:197`：

```swift
// 指定了菜系卻一家都沒有，退回查一般餐廳而不是直接失敗。
if places.isEmpty, !keyword.isEmpty {
    places = (try? await searchPlaces(dish: "餐廳", near: location)) ?? []
}
```

**這個退回不會在畫面上說。** 但產品規則第三條是：

> 放寬條件時要老實說明放寬了哪個維度 —— 不能默默給不符合的東西

「吃什麼」模式嚴格遵守（`relaxedDimensions` → `NoticeBox`）。
「去哪吃」模式**沒有**，而且 `findRestaurants()` 開頭就把 `relaxedDimensions` 清空，
連提示的機制都關掉了。

> 注意：kuoyo 遇到的情況**可能根本沒走到這條** —— MapKit 回了非空的不相關結果，
> 退回不會觸發，畫面上更不會有任何說明。兩條路徑都要處理。

---

## 四、決定的做法

### 1. 把菜系降級為「搜尋關鍵字」（UI 用語）

「去哪吃」模式下，那一列的標題不再叫「菜系」。使用者要知道**這是拿去搜店名的字，
不是店家分類的保證**。具體用語由設計師定。

### 2. 退回一般餐廳時必須顯示提示

沿用「吃什麼」模式已有的 `NoticeBox`，例如：

> 附近找不到「歐陸」的店，改為顯示一般餐廳。

實作上可以讓 `NearbySearchModel` 回報「有沒有走退回」，`RotateViewModel` 據此設狀態，
**不要新造一套提示機制**。

### 3. 幾個查不到的菜系做搜尋詞翻譯表

把「歐陸」這種 MapKit 比對不到的詞，翻成它找得到的說法（例如「西餐廳」）。

**這張表要當成「搜尋詞翻譯」寫在明處，不是假裝在篩菜系。** 註解要寫清楚它的性質，
否則下一個人會以為那是分類邏輯。

需要實測才知道哪幾個要翻譯。初步的懷疑名單（**要實測，不要照抄**）：

| 可能沒問題 | 可能要翻譯 |
|---|---|
| 台式、日式、韓式、義式、美式 | 中式、東南亞、南亞、歐陸、墨西哥 |

### 4. 不做的事

- **不要用關鍵字過濾 MapKit 的回傳結果。** 那是「用一層猜測修另一層猜測」，
  正是 `大改紀錄` 第一節拿掉 `DietaryFilter` 的理由。店名裡沒有菜系資訊，濾不出真相。
- 不要為此接 Google Places API（需要金鑰與計費，且 Android 移植要再一把）。

---

## 五、驗收標準

1. 選「歐陸」後，畫面上**看得出來**結果是怎麼來的（找到了／退回了）
2. 退回一般餐廳時有提示，措辭與「吃什麼」模式的放寬提示一致
3. 「吃什麼」模式行為零變化
4. 翻譯表有註解說明它是搜尋詞翻譯，不是分類邏輯
5. 十個菜系逐一實機測過，記錄哪些 MapKit 找得到、哪些要翻譯
