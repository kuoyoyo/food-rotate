## 〇、你的根因判讀我確認了，是對的

> 那個方向 guard 擋住的是「改不改 `swipeOffset`」，不是「這個手勢要不要接手」。

正確。`DragGesture(minimumDistance: 12)` 一旦跨過 12pt 就已經進場，
`guard` 只是讓它在 changed 狀態裡什麼都不做 —— 但 `ScrollView` 的 pan 已經被擋在外面。
慢慢拖必定先跨過 12pt，所以慢速必卡；快速 fling 時捲動先贏，所以快的又是好的。

**這是我的錯，而且錯在「我以為判斷方向就等於讓出手勢」。**

## 一、做法：不再自己仲裁方向

我沒有去修那個 guard，而是**把整個自製手勢拿掉**，改用**巢狀的水平 `ScrollView`**：

```
ScrollView(.horizontal) {
    HStack {
        列本體.containerRelativeFrame(.horizontal)   // 佔滿容器寬
        deleteAction                                 // 96pt
    }
    .scrollTargetLayout()
}
.scrollTargetBehavior(.viewAligned)   // 只停在「收合」與「完全露出」
.scrollDisabled(!canDelete)           // 剩兩道時整列不該滑得動
```

**方向仲裁交給 UIKit** —— 巢狀捲動視圖依主要方向決定給內層還是外層，
那是原生滑動列本來就在用的機制。

### 為什麼是這個做法，不是把門檻改成「水平位移超過某值」

你給的兩個方向我都想過。改門檻仍然是**我自己在仲裁**：
還是得決定多少算水平、對角線怎麼算、以及仲裁錯的時候會不會又卡住。

而這一塊我已經連錯三次手勢的掛法（`.swipeActions` 掛在非 `List`、
靜止態的圓角同心、現在這個方向仲裁）。**三次都是「編得過、測試綠、實機不對」。**
再寫第四版自製仲裁，我沒有理由相信這次會對。

你自己也點出 S3 那個做法搬不過來 —— 那次兩者同方向，只要決定誰處理；
這次方向相反，是不同的問題。**把它交給平台，是這三次教訓的結論。**

## 二、⚠️ 測試數從 51 掉到 43，這是刻意的

`RowSwipe` 的 `offset(base:translation:)` 與 `resolve(offset:)` 是**自製仲裁時代的產物** ——
現在停的位置由 `scrollTargetBehavior` 決定，沒有需要自己算的數字。
那 8 支測試測的東西已經不存在了。

**我把那個檔刪掉了，沒有留著讓它綠。** 測一個不再被呼叫的函式，比沒有測試更糟：
它會讓人以為這一塊有防護。

`RowSwipe` 只留下還在用的 `actionWidth`。

驗收標準第 6 項寫「51 個測試全過」，實際是 **43 個全過**。差額就是這 8 支，
不是有測試壞掉。

## 四、⚠️ 我驗不到的 —— 而這次正好是驗收的全部

驗收標準的六項裡，**第 1、2、3、4、5 項都需要真的用手指拖曳**，我沒有工具。

我要把話說清楚：**這次我連「原理上會生效」的自證都比上次弱。**
上一輪我至少能用「預設滑開」證明位移與外觀會動；這次外觀我一樣驗了，
但「慢速垂直拖曳會不會捲動」這件事的正確性，**完全建立在「UIKit 的巢狀捲動仲裁是對的」
這個前提上**，而不是我觀察到的行為。

那個前提我認為成立（它是系統機制、原生滑動列就是這樣做的），但它是**推論不是觀察**。

請你用慢速多段拖曳實測第 1–5 項。

### 一個已知的行為差異，先講

改寫前：滑開之後點列會先收回去。
改寫後：**滑開之後點列會展開優缺點，列維持在滑開的位置**（要收回去得往回滑）。

原因是位置現在由 `ScrollView` 持有，要在點擊時收回得再接一個 `ScrollPosition` 綁定。
我沒有加 —— **那又是一段我測不到的互動邏輯**，寧可先維持簡單、由你看實機決定要不要補。
